# 친환경 차량·전기차 충전소 상태 API 조사 및 연동 명세

## 요약

**결론:** 충전소 위치와 충전기 상태를 확인하는 읽기 전용 MVP는 **한국환경공단 `한국환경공단_전기자동차 충전소 정보` API**를 1순위로 채택한다. 현재 공식 페이지가 제시하는 상태 API는 `HTTPS REST + XML`이며, `ServiceKey`, 페이지네이션, 지역코드(`zcode`), 상태갱신 기간(`period`)을 사용하고 `statUpdDt`를 통해 상태 신선도를 판단할 수 있다. 개발계정 호출 한도는 1,000회이고 운영계정은 활용사례 등록 후 증량 신청이 가능하므로, 서버가 직접 외부 API를 매 요청마다 호출하지 말고 **수집기 → 정규화 저장소 → 내부 조회 API**로 분리한다. [C-001][C-002][C-003]

`keco-api`는 공식 데이터셋 명칭과 제공기관을 기준으로 **KECO(한국환경공단) 계열 API를 지칭한 표현**으로 해석했다. 공식 API 명칭은 `한국환경공단_전기자동차 충전소 정보`이고, 호출 서비스는 `B552584/EvCharger`이다. 별도의 패키지명·저장소명 `keco-api`는 확인하지 못했다.

환경부·국립환경과학원의 **전기차 1회충전주행거리 인증정보 API**는 차량 모델·인증·주행거리 데이터에 적합하지만 충전기 실시간 상태의 대체재가 아니다. 인증 완료 차량만 조회되고 인증 반납·취소 차량 및 일부 과거 전산 미등록 인증서는 제외된다. [C-005]

대안은 다음처럼 역할을 구분한다.

- **KSGA 전기차 충전기 정보 API:** 충전사업자들의 위치·상태를 JSON으로 제공하는 보완 소스. 신청·승인·Service Key·접근 IP가 필요하고 1일 500회 제한이 명시되어 있다. [C-006]
- **한국전력공사 전기차 충전소 설치현황:** 설치장소와 급속·완속 충전기 대수 중심의 정적/현황 데이터. 실시간 충전기 상태 소스로 채택하지 않는다. [C-007]
- **OCPI/OCPP:** OCPI는 CPO↔MSP 사업자 간 로밍·상태·세션 교환, OCPP는 충전기↔CSMS 장비 운영 프로토콜이다. 공개 조회 API와 혼동하지 말고, 직접 충전망을 운영하거나 로밍 계약을 맺을 때만 별도 범위로 도입한다. [C-008][C-009]

## 조사 질문

1. 한국환경공단·환경부 및 주요 대안 API 중 충전소 위치·충전기 상태 확인에 적합한 후보는 무엇인가?
2. 일반 웹/서버 백엔드에서 각 API를 어떤 경계, 데이터 모델, 통신·오류 계약으로 연동해야 하는가?
3. 데이터 신선도, 호출량, 인증키, 장애·중복·소스 충돌을 어떤 운영 방침으로 통제해야 하는가?

## 질문에 대한 이해 및 분석

- **독자/결정:** 개발팀·아키텍처 결정. 단순 API 목록이 아니라 구현 가능한 연동 계약과 선택 조건이 필요하다.
- **보고서 형식:** API 연동 명세서. 공식 자료와 실제 활용 표면을 우선하며, 확인된 사실과 권고 설계를 구분한다.
- **용어 해석:** `친환경 차량`은 차량 인증·주행거리 메타데이터를 포함하고, `충전소 상태`는 충전소/충전기 위치·운영·가용 상태를 포함하는 것으로 해석했다.
- **중요한 구분:** 충전기 상태 조회(공공/사업자 REST API), 사업자 간 로밍(OCPI), 충전기 장비 제어(OCPP)는 서로 다른 계층이다.

## 배경

현재 저장소는 NestJS 기반 서버·stdio·CLI 애플리케이션과 MCP runtime을 보유하고, 지도 provider를 공통 `Provider` 인터페이스와 순서 기반 fallback으로 묶는다. 따라서 충전 데이터도 기존 지도 provider에 억지로 넣기보다는 충전소 도메인과 충전 provider 계층을 별도로 두고, 필요한 경우 장소 검색과 좌표를 연결하는 편이 경계상 안전하다. [C-010]

## 범위와 방법

- **범위:** 한국환경공단(질문의 `keco-api` 해석), 환경부·국립환경과학원 차량 인증 API, KSGA 충전사업자 API, 한국전력공사 현황 데이터, OCPI/OCPP 역할·통신 규약, 현재 저장소의 연동 경계.
- **Source lane:** 저장소 파일 + 공식 공공데이터포털 + 제공기관 공식 페이지·가이드 + 표준 제정기관 공식 페이지. 공공데이터포털의 공식 활용사례 목록을 실사용 표면의 보조 근거로 사용했다.
- **제외 또는 민감도 제한 자료:** `.env`와 API 키·개인정보·인증정보는 읽거나 기록하지 않았다. 특정 충전사업자의 비공개 API와 계약별 SLA·가격은 공개 근거가 없어 일반화하지 않았다.
- **조사 기준일:** 2026-08-14. 페이지의 최종 수정일은 출처별로 다르며, 상세 값은 출처 원장에 기록했다.
- **방법:** 사용자 intake 후 후보를 공공데이터/사업자/표준 계층으로 분해하고, 공식 페이지에서 엔드포인트·필드·쿼터·라이선스·오류를 직접 확인했다. 저장소에서는 최소 범위의 구조·패키지·provider 계약만 확인했다. 검색 결과는 후보 발견에만 사용하고 핵심 주장은 원문 관찰에 연결했다.
- **사전 조사 intake:** 표면: `interview-technical`; 질문 수: 5; 사용자 결정: 개발팀·아키텍처 결정, API 연동 명세서, 공식+실사용 사례, Keco+환경부+주요 대안, 일반 웹/서버 백엔드.
- **사전 조사 보고서 품질 답변:** 의사결정과 독자: 개발팀·아키텍처 결정; 보고서 형식: API 연동 명세서; 품질 요구사항: 공식 출처와 실제 활용 사례를 함께 사용.
- **사전 조사 명확화:** `interview-technical`; 1 round(s); handoff: 없음; 영향: 구현 계약·실패 동작·신선도·호환성·관찰 가능한 검증을 보고서에 포함했다.
- **범위 변경:** 없음. 다만 공개 문서에서 확인되지 않은 세부 상태코드 의미와 차량 인증 API의 실제 서비스 URL은 명시적 제한으로 남겼다.

## 핵심 발견

### C-001 — 한국환경공단 API는 충전소 정보와 상태를 제공한다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 제공기관 공식 공공데이터포털 페이지의 데이터 설명·기관·서비스 URL을 직접 확인했다.
- **근거:** `한국환경공단_전기자동차 충전소 정보`는 위치, 운영기관, 충전기 ID·타입·용량·방식, 이용조건과 충전기 상태갱신 정보(`stat`, `statUpdDt` 등)를 제공한다. 제공기관은 한국환경공단, 표준데이터 제공 시스템은 ev.or.kr이다. [S-006](https://www.data.go.kr/data/15076352/openapi.do) [S-015](https://www.data.go.kr/data/15013115/standard.do)
- **제한:** 공개 페이지는 상태코드 숫자의 의미표를 현재 본문에 모두 싣지 않는다. 제품 표시명 매핑은 최신 활용가이드와 실제 샘플로 별도 검증해야 한다.

### C-002 — 상태 조회의 공식 요청·응답 계약은 HTTPS REST/XML이다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 공식 API 활용명세의 요청주소, 요청변수, 응답필드를 확인했다.
- **근거:** 요청주소는 `https://apis.data.go.kr/B552584/EvCharger/getChargerStatus`이다. 필수는 `ServiceKey`, `pageNo`, `numOfRows`; 선택은 `period`(기본 5분, 1~10분)와 `zcode`이다. 응답에는 `resultCode`, `resultMsg`, `pageNo`, `numOfRows`, `totalCount`, `busiId`, `statId`, `chgerId`, `stat`, `statUpdDt`가 있다. [S-006](https://www.data.go.kr/data/15076352/openapi.do)
- **제한:** 공식 페이지의 기본 데이터 포맷은 XML이다. JSON을 전제로 한 구현은 하지 말고 실제 활용가이드·승인 후 서비스 응답으로 확인한다.

### C-003 — 호출량·인증·게이트웨이 오류를 설계에 반영해야 한다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 공공데이터포털 공식 조건과 오류코드 표에 근거한다.
- **근거:** 비용은 무료, 출처표시 제1유형이며 개발계정 신청 가능 트래픽은 1,000회, 운영계정은 활용사례 등록 후 증량 신청이 가능하다. 공식 오류에는 잘못된 파라미터(10), 서비스 폐기/오타(12), 키 누락·권한(20), 일일 한도 초과(22), 초당 한도 초과(23), 차단 IP(29), 미등록 키(30), 만료 키(31), 타임아웃(05)이 포함된다. [S-006](https://www.data.go.kr/data/15076352/openapi.do)
- **제한:** 한도는 계정·운영정책에 따라 바뀔 수 있으므로 배포 전 포털에서 재확인한다.

### C-004 — 구형 자동변환 URL이 아니라 현재 EvCharger 서비스로 전환해야 한다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 공공데이터포털의 폐기·변경 공지를 확인했다.
- **근거:** 과거 `http://api.data.go.kr/openapi/tn_pubr_public_elcty_car_chrstn_api`에서 변경되었고, 공지는 상태 `getChargerStatus`와 정보 `getChargerInfo`의 새 호출 URL 및 `전국전기차충전소표준데이터`로의 재신청을 안내한다. 현재 상세 페이지는 HTTPS URL을 제시한다. [S-007](https://www.data.go.kr/bbs/ntc/selectNotice.do?originId=NOTICE_0000000002460) [S-006](https://www.data.go.kr/data/15076352/openapi.do)
- **제한:** 기존 사용자는 구 API가 당장 동작할 수 있다는 공지 문구가 있으므로, 마이그레이션 시점·키 재신청을 운영팀과 확인한다. 신규 구현은 구 URL을 사용하지 않는다.

### C-005 — 환경부·국립환경과학원 차량 인증 API는 차량 메타데이터용이다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 제공기관 공식 API 페이지와 메타데이터를 직접 확인했다.
- **근거:** REST/XML API이며 상온·저온 도심/고속/복합 1회충전주행거리, 업체명, 인증번호·일자, 차종·자동차명·전기차형식·연료·인증구분을 제공한다. 인증완료 상태만 조회되고 인증 반납·취소 및 전산 미발급 과거 인증서는 제외된다. 개발계정 10,000회, 무료·출처표시 조건이다. [S-008](https://www.data.go.kr/data/15119895/openapi.do)
- **제한:** 조회 서비스의 실제 요청주소·상세 파라미터가 공개 페이지의 동적 활용명세에 노출되지 않아 이 보고서에 추정 URL을 넣지 않았다. 차량 카탈로그 연동 전 승인 후 가이드/Swagger를 확보해야 한다.

### C-006 — KSGA는 사업자 상태를 보완하는 승인형 JSON API다

- **Claim type:** `direct_fact`
- **신뢰도:** high — KSGA 공식 API 신청 페이지와 신청 가이드를 확인했다.
- **근거:** 전기차 충전 서비스 사업자의 충전소 위치·상태를 REST/JSON으로 제공한다. 회원가입, Open API 신청, 승인 검토, 승인완료 후 Service Key 발급 절차이며 접근 IP·신청사유를 입력한다. 트래픽 제한은 500회/일, 무료·이용허락 제한 없음으로 표시된다. [S-010](https://chargeinfo.ksga.org/front/cs/api/infomation) [S-011](https://chargeinfo.ksga.org/resources/doc/OpenApi_ApplyGuide.pdf)
- **제한:** 실제 endpoint, JSON 스키마, 사업자별 갱신 SLA는 로그인 후 발급되는 이용가이드·계약 범위에서 확인해야 한다.

### C-007 — 한국전력공사 데이터는 설치현황 중심이다

- **Claim type:** `direct_fact`
- **신뢰도:** high — 공공데이터포털의 공식 메타데이터를 확인했다.
- **근거:** `한국전력공사_전기차 충전소 설치현황`은 설치장소와 급속·완속 충전기 대수를 제공하며, 전력데이터개방포털 회원가입 후 이용한다. 포맷은 JSON+XML로 표시된다. [S-009](https://www.data.go.kr/catalog/15101407/openapi.json)
- **제한:** 설치현황과 현재 가용 여부를 혼합하지 않는다. 실시간 상태를 제공하는지 별도 계약으로 확인되지 않는 한 보조 통계로만 사용한다.

### C-008 — OCPI는 CPO↔MSP 사업자 간 공개 로밍 계약이다

- **Claim type:** `direct_fact`
- **신뢰도:** high — EVRoaming Foundation 공식 페이지를 확인했다.
- **근거:** OCPI는 eMobility Service Provider와 Charge Point Operator를 연결하며 위치·가용성·요금·인증·예약·세션·CDR·원격 시작/중지 등을 교환한다. 공식 현재 버전은 2.3.0이고, 2.3.0은 EU NAP·차량 유형·PnC·결제/예약 선택 모듈을 포함한다. [S-012](https://evroaming.org/ocpi/) [S-013](https://evroaming.org/ocpi-downloads/)
- **제한:** 한국환경공단 공개 API를 OCPI endpoint로 간주할 근거는 없다. OCPI는 상대 사업자와 버전·역할·인증을 합의한 뒤 도입한다.

### C-009 — OCPP는 충전기↔CSMS 장비 운영 프로토콜이다

- **Claim type:** `direct_fact`
- **신뢰도:** high — Open Charge Alliance 공식 FAQ를 확인했다.
- **근거:** OCPP 1.6은 SOAP와 JSON over WebSocket을 지원하고, OCPP 2.0.1은 JSON over WebSocket만 사용하며 1.6과 호환되지 않는다. OCPP 2.1은 2.0.1 기반으로 하위 호환되며 V2G·DER·배터리 교환 등 기능을 추가한다. OCA는 1.6·2.0.1용 공식 적합성 테스트 도구를 제공한다. [S-014](https://openchargealliance.org/faq/)
- **제한:** 일반 서버가 공공 충전소 상태를 조회하는 MVP에는 OCPP 서버를 구현하지 않는다. 직접 CSMS를 운영할 때 별도 인증·WebSocket·적합성 범위를 결정한다.

### C-010 — 현재 저장소에는 별도 충전 도메인과 provider 계층이 맞다

- **Claim type:** `inference`
- **신뢰도:** medium — 현재 repository 구조와 기존 provider 계약에서 도출한 설계 판단이다.
- **근거:** 현재 `Provider`는 `resolve`, `searchNearby`, `geocode`만 정의하고, provider router는 설정 순서와 실패 fallback을 소유한다. NestJS·Axios·Zod가 이미 의존성에 있다. [S-002](package.json) [S-003](libs/map-providers/src/typed.ts) [S-004](libs/map-providers/src/provider-router.ts) [S-005](docs/multi-app-architecture.md)
- **제한:** 실제 충전 기능 요구사항·DB가 아직 없으므로 아래 구조는 구현 전 설계안이다.

### 2. 한국환경공단 호출 명세

#### 2.1 상태 조회

```http
GET https://apis.data.go.kr/B552584/EvCharger/getChargerStatus
    ?ServiceKey=<SERVICE_KEY>
    &pageNo=1
    &numOfRows=9999
    &period=5
    &zcode=11
Accept: application/xml
```

- `ServiceKey`: 공공데이터포털 발급 키. 로그·트레이스·에러 메시지에서 query 전체를 마스킹한다.
- `pageNo`: 페이지 번호.
- `numOfRows`: 10 이상 9,999 이하. 전체 건수는 `totalCount`로 확인하고 페이지를 끝까지 순회한다.
- `period`: 상태갱신 조회 범위(분), 1~10, 기본 5. 이는 **조회 조건**이지 내부 표시의 신선도 보장시간이 아니다.
- `zcode`: 시·도 코드. 지역 단위 수집·쿼터 분산에 사용하되, 실제 지역 코드 목록은 운영 설정으로 관리한다.

응답 처리의 최소 계약은 다음과 같다.

```xml
<response>
  <header>
    <resultCode>00</resultCode>
    <resultMsg>OK</resultMsg>
  </header>
  <body>
    <items>
      <item>
        <busiId>ME</busiId>
        <statId>28260005</statId>
        <chgerId>02</chgerId>
        <stat>2</stat>
        <statUpdDt>20190829121020</statUpdDt>
      </item>
    </items>
  </body>
</response>
```

위 XML은 공식 명세에 표시된 필드명·샘플 형식을 보여주는 계약 예시다. `stat`의 숫자 의미는 최신 가이드에서 확인되기 전까지 원문값으로 저장하고, UI 표시명은 버전별 매핑 설정으로 분리한다. `statUpdDt`는 `yyyyMMddHHmmss` 형식으로 파싱하고 파싱 실패 시 `UNKNOWN`으로 격하한다.

#### 2.2 기본 정보 조회

```http
GET https://apis.data.go.kr/B552584/EvCharger/getChargerInfo
    ?ServiceKey=<SERVICE_KEY>
    &pageNo=1
    &numOfRows=<PAGE_SIZE>
```

공식 변경 공지로 endpoint 자체는 확인했지만, 현재 공개 페이지에서 `getChargerInfo`의 전체 요청·응답 표가 동일하게 노출되지는 않았다. 따라서 다음을 구현 전 필수 작업으로 둔다.

1. 공공데이터포털의 현재 `v1.25` 활용가이드를 내려받아 정보 API의 필드·필수 파라미터를 고정한다.
2. 실제 승인 키로 소량 호출해 XML fixture를 저장한다(키 제거 후).
3. `statId + chgerId` 또는 제공기관이 정의한 안정 ID를 상태와 정보의 join key로 검증한다.
4. 정보 변경(주소·운영시간·충전기 타입)과 상태 변경을 서로 다른 upsert 경로로 저장한다.

### 3. 정규화 데이터 계약

외부 API별 원문을 그대로 내부 API에 노출하지 않고 다음 공통 모델로 정규화한다.

```ts
type ChargerStatus = {
  source: 'keco' | 'ksga' | 'other'
  operatorId?: string
  stationId: string
  chargerId: string
  rawStatus: string | null
  normalizedStatus:
    | 'AVAILABLE'
    | 'CHARGING'
    | 'UNAVAILABLE'
    | 'MAINTENANCE'
    | 'UNKNOWN'
    | null
  statusUpdatedAt: string | null
  observedAt: string
  freshness: 'FRESH' | 'STALE' | 'UNKNOWN'
}

type ChargerStation = {
  source: string
  operatorId?: string
  stationId: string
  name?: string
  address?: string
  lat?: number
  lng?: number
  access?: 'PUBLIC' | 'RESTRICTED' | 'UNKNOWN'
  chargers: ChargerStatus[]
  sourceObservedAt: string
  rawVersion?: string
}
```

정규화 규칙:

- 원천 식별자(`busiId`, `statId`, `chgerId`)를 보존하고, 추정한 단일 숫자 ID로 덮어쓰지 않는다.
- 좌표·주소가 없는 상태 응답은 위치 검색 결과에서 제외할 수 있지만 상태 이력은 버리지 않는다.
- `observedAt`(우리 수집 시각)와 `statusUpdatedAt`(원천 갱신 시각)을 항상 분리한다.
- `statusUpdatedAt`이 내부 TTL을 넘으면 `STALE`; 원천 값이 없거나 파싱 실패면 `UNKNOWN`으로 표시한다. stale 데이터를 `AVAILABLE`로 노출하지 않는다.
- 소스 간 같은 충전기를 합칠 때 사업자·충전소·충전기 ID를 모두 비교한다. 충돌 시 최신 시각이 무조건 우선이라는 규칙을 적용하지 말고, 소스 우선순위와 freshness를 함께 기록한다.

### 4. 권장 서버 아키텍처

```text
[Keco XML]      [KSGA JSON]      [Vehicle XML]
     │               │                 │
     └──── provider adapter / schema validator ────┐
                                                   │
                                  normalized charger/vehicle domain
                                                   │
                            cache + durable snapshot + freshness index
                                                   │
                    internal JSON API / MCP tool / scheduled collector
```

저장소 적용안:

- `libs/charger-providers`: `KecoChargerProvider`, `KsgaChargerProvider`와 외부 응답 파서.
- `libs/charger-domain`: 정규화 타입, 상태 신선도, source conflict 정책, 조회 유스케이스.
- `apps/http-server` 또는 별도 worker: 수집 스케줄·rate limit·재시도·metrics.
- `mcp-runtime`: `charger_search_nearby`, `charger_status` 같은 tool 등록이 필요할 때만 domain service를 호출.
- 기존 `libs/map-providers`의 `Provider`에 charger 상태 메서드를 추가하지 않는다. 지도 장소 검색의 `resolve/searchNearby/geocode`와 충전기 상태의 pagination/freshness 계약이 다르기 때문이다. [C-010]

### 5. 내부 API 계약 예시

```http
GET /v1/charging-stations?lat=37.5665&lng=126.9780&radiusM=3000&status=AVAILABLE
```

```json
{
  "items": [
    {
      "stationId": "ME:28260005",
      "name": "...",
      "location": { "lat": 37.5665, "lng": 126.9780 },
      "chargers": [
        {
          "chargerId": "02",
          "status": "UNKNOWN",
          "rawStatus": "2",
          "freshness": "STALE",
          "statusUpdatedAt": "20190829121020",
          "observedAt": "2026-08-14T00:00:00Z"
        }
      ]
    }
  ],
  "sourceSummary": { "keco": { "observedAt": "2026-08-14T00:00:00Z" } }
}
```

내부 응답은 `source`, `rawStatus`, `statusUpdatedAt`, `freshness`를 숨기지 않는다. 사용자가 “사용 가능”으로 판단할 때 데이터 시각을 볼 수 있어야 하며, stale/unknown을 빈 목록으로 위장하지 않는다.

## 분석

### 1. 선택 조건

- **읽기 전용 전국 상태 조회:** Keco 단독으로 시작한다. 공식 계약과 상태 시각이 확인되고, 공개 공공데이터로 접근성이 가장 높다.
- **사업자별 누락·지연 보완:** KSGA를 2차 소스로 붙이되, 실제 JSON schema·갱신주기·사업자 범위를 확인한 뒤에만 병합한다.
- **차량 모델 검색:** NIER 인증 API를 별도 `VehicleCatalogProvider`로 둔다. 충전기 상태 adapter와 공유하지 않는다.
- **직접 충전기 관제:** OCPP 2.0.1/2.1 검토로 승격한다. 공공 REST API를 polling하는 설계와는 별도 프로젝트다.
- **로밍·결제·세션:** 상대 CPO/MSP가 OCPI 2.3.0을 제공할 때 OCPI adapter를 별도로 정의한다. OCPP를 OCPI 대체로 사용하지 않는다.

### 2. 수집·캐시·신선도 정책

1. 기본은 수요 기반 지역 수집과 짧은 캐시다. 모든 지역을 고정 1분 polling하지 않는다.
2. Keco 상태 요청의 `period`는 1~10분 범위에서 수집 창으로 사용하고, 내부 `freshness TTL`은 서비스 UX·쿼터·장애 상황을 기준으로 별도 설정한다.
3. 정상 수집 성공 시 원천 `statUpdDt`와 수집 시각을 저장한다. 다음 수집에서 데이터가 없더라도 이전 상태를 최신으로 연장하지 않는다.
4. `STALE` 데이터를 반환할 때 마지막 관측 시각과 소스명을 함께 표시한다.
5. 정보 스냅샷과 상태 스냅샷을 분리하고, 상태는 `(source, operatorId, stationId, chargerId)` 키로 upsert한다.
6. 공공 API 응답은 사용자 요청 경로에서 직접 호출하지 않는다. 수집기가 quota를 통제하고 내부 API는 cache/snapshot을 읽는다.

### 3. 오류·재시도 정책

| 오류 | 분류 | 정책 |
|---|---|---|
| HTTP timeout / `SERVICETIMEOUT_ERROR(05)` | 일시적 | exponential backoff + jitter, 제한된 횟수 재시도. stale snapshot을 `STALE`로 반환 |
| `APPLICATION_ERROR(01)` | 일시적/원인 미상 | 짧은 1회 재시도 후 circuit 기록 |
| `INVALID_REQUEST_PARAMETER_ERROR(10)` | 영구적 요청 오류 | 재시도 금지, adapter validation 수정 |
| `NO_OPENAPI_SERVICE_ERROR(12)` | 계약/폐기 | 즉시 중단·알림, endpoint/버전 확인 |
| 키 누락·권한 `20`, 미등록 `30`, 만료 `31` | 설정/권한 | 재시도 금지, secret/config 운영 알림 |
| 일일 한도 `22` | quota | 해당 provider 수집 중지, 다음 reset 또는 증량 승인 대기 |
| 초당 한도 `23` | rate limit | Retry-After가 있으면 준수, 없으면 지수 backoff·동시성 축소 |
| 차단 IP `29` | 네트워크 정책 | 재시도 금지, egress IP와 신청 정보를 확인 |
| XML/JSON schema parse 실패 | 계약 변경 | raw 원문은 제한적으로 격리, 정상 snapshot을 연장하지 않고 `UNKNOWN`/`STALE` 처리 |

`resultCode`가 성공이 아니면 HTTP 200이어도 성공으로 취급하지 않는다. 반대로 HTTP 오류와 게이트웨이 body 오류를 분리해 metrics에 기록한다.

### 4. 인증·보안 방침

- Service Key는 secret manager 또는 환경변수로 주입하고 코드·문서·fixture·로그에 기록하지 않는다.
- Keco는 공식 요청 필드가 query의 `ServiceKey`이므로 URL 로거와 tracing span에서 query를 전부 redact한다. 키를 일반 query cache key로 사용하지 않는다.
- KSGA는 신청한 접근 IP와 실제 egress IP를 일치시킨다. NAT·proxy 변경을 배포 절차에 포함한다.
- 외부 통신은 HTTPS를 사용하고 TLS 검증을 끄지 않는다. 인증서 오류를 fallback으로 숨기지 않는다.
- MVP는 읽기 전용 상태·정보 조회만 허용한다. 원격 시작/중지, 결제, 사용자 토큰, 차량 식별정보는 범위 밖이다.
- OCPI/OCPP 도입 시 인증서·토큰·역할·권한·감사로그를 별도 threat model로 검토한다.

### 5. 데이터 품질·소스 충돌 방침

- 필수 식별자와 시각이 없는 레코드는 내부 조회에서 `UNKNOWN`으로 남기고 자동 삭제하지 않는다.
- 상태 숫자 매핑은 소스 버전별 설정으로 관리한다. 최신 공식 가이드에 없는 상태는 `UNKNOWN`으로 보존한다.
- Keco와 KSGA가 같은 지점으로 보이는 경우 주소·좌표 근접성만으로 자동 병합하지 않는다. 사업자/충전소/충전기 ID가 없는 병합은 후보 관계로만 표시한다.
- 소스 우선순위는 “Keco가 항상 진실”처럼 고정하지 말고, 소스별 coverage·freshness를 계산해 응답에 포함한다.
- 위치 정보 변경과 상태 변경을 서로 다른 이벤트로 처리하면 오래된 위치가 최신 상태를 덮는 문제를 피할 수 있다.

## 대안

### A. Keco 단독 MVP

- **적용:** 전국 검색과 현재 상태 표시가 목표이고 서버가 충전기 장비를 직접 운영하지 않을 때.
- **장점:** 공식 계약·상태갱신 시각·공공 접근성·무료 조건.
- **단점:** XML 파싱, quota, 공개 페이지에서 확인되지 않은 상태코드 의미, 정보 endpoint 상세계약 확인 필요.

### B. Keco + KSGA 이중 소스

- **적용:** 특정 사업자 또는 지역에서 Keco 누락/지연을 관찰한 뒤 보완이 필요할 때.
- **장점:** JSON 사업자 데이터와 교차검증 가능.
- **단점:** 500회/일, 신청·승인·접근 IP, 사업자별 schema·갱신주기 확인 비용. 같은 충전기를 중복 집계할 위험.

### C. OCPI 파트너 연동

- **적용:** 로밍, 요금, 세션, CDR, 인증·예약이 제품 범위일 때.
- **장점:** 역할과 모듈이 표준화되고 실시간 상태·세션을 사업자 간 교환할 수 있음.
- **단점:** 공개 API 키만으로 해결되지 않으며 CPO/MSP 역할·버전·endpoint·토큰·SLA를 계약해야 함.

### D. OCPP CSMS 구축

- **적용:** 충전기 장비를 직접 연결해 원격 운영·계측·펌웨어·스마트충전을 해야 할 때.
- **장점:** 장비 운영에 필요한 표준 명령·이벤트·보안·적합성 시험 경로.
- **단점:** WebSocket 서버, 장비 인증서, 연결 상태 머신, 적합성 테스트와 운영 보안이 필요하며 일반 조회 API보다 큰 범위.

## 실행상 고려사항

### 구현 순서

1. `ChargerStatusProvider`/`ChargerInfoProvider`/`VehicleCatalogProvider` 인터페이스와 정규화 타입을 먼저 고정한다.
2. Keco XML parser와 공식 필드 fixture를 작성한다. 파싱 결과에 `rawStatus`, `statusUpdatedAt`, `observedAt`를 모두 남긴다.
3. 페이지네이션·지역 분할·수집 lock·quota guard를 넣는다.
4. 저장소 upsert와 freshness index를 구현한다.
5. 내부 `/v1/charging-stations` 또는 MCP tool은 snapshot만 조회한다.
6. 오류코드별 retry/circuit/alert를 통합한다.
7. 승인 키를 사용하는 live smoke test는 opt-in으로 분리하고 CI 기본 실행에서는 외부 API를 호출하지 않는다.

### 관찰 가능성

- provider, endpoint, region, resultCode, HTTP status, latency, item count, observedAt, sourceUpdatedAt, freshness를 metric/tag로 남긴다.
- ServiceKey, Authorization, 원문 URL query는 절대 로그하지 않는다.
- 알림 기준: 연속 timeout, schema parse failure, key/permission error, quota 22/23, stale 비율 상승, 전체 지역 수집 누락.
- 사용자 응답에는 `dataAsOf`, `source`, `freshness`를 제공한다.

### 검증 기준

- 공식 성공 XML(`resultCode=00`)을 전체 페이지로 파싱한다.
- `pageNo`, `numOfRows`, `period` 경계값과 잘못된 지역코드를 검증한다.
- 오류 05/10/12/20/22/23/29/30/31에 대해 재시도 여부가 기대값과 일치한다.
- `statUpdDt`가 TTL을 넘거나 형식이 깨진 경우 `STALE`/`UNKNOWN`을 반환한다.
- 중복 `(source, operatorId, stationId, chargerId)` upsert가 레코드를 늘리지 않는다.
- 키가 로그·오류·트레이스·fixture에 남지 않는다.
- 외부 키가 없는 기본 CI는 parser/domain 테스트를 통과하고, 키가 있는 환경에서만 실제 endpoint smoke를 실행한다.

## 근거 불확실성

- **상태코드 의미표:** 현재 확인한 공식 상세 페이지는 `stat` 필드와 샘플값은 제공하지만 모든 숫자별 표시명은 제공하지 않았다. 따라서 이 보고서는 특정 숫자를 `AVAILABLE` 등으로 단정하지 않는다. 이것이 가장 큰 구현 한계다.
- **`getChargerInfo` 상세계약:** 공식 변경 공지에서 endpoint는 확인했으나 현재 페이지에서 전체 요청·응답 표가 동일하게 노출되지 않았다. 최신 활용가이드와 승인 후 샘플을 받아야 한다.
- **차량 인증 API endpoint:** 공식 데이터셋의 기능·필드·제약·포맷은 확인했으나 동적 활용명세의 실제 요청주소는 관찰하지 못했다. 추정 URL을 작성하지 않았다.
- **실시간성:** `period`와 `statUpdDt`는 원천 갱신·조회 조건이지 서비스 수준의 SLA가 아니다. “실시간”이라는 표현을 사용자에게 그대로 보장하지 말고 `dataAsOf`와 freshness를 노출한다.
- **KSGA coverage:** 공식 페이지는 위치·상태 API와 신청 조건을 설명하지만 사업자별 커버리지·schema·갱신 SLA는 로그인/승인 후 자료에 있다.
- **현재성:** 페이지 수정일과 실제 서비스 응답은 변할 수 있다. 배포 전 각 포털의 endpoint·쿼터·가이드 버전을 재확인한다.

질문별 결과 상태:

| 질문 | 상태 | 판단 |
|---|---|---|
| 후보 API와 역할 비교 | `sufficient` | Keco 1순위, KSGA 보완, KEPCO 현황, NIER 차량 메타데이터의 역할을 공식 근거로 구분했다. |
| 구현·통신 규약 | `sufficient` | Keco REST/XML와 KSGA REST/JSON, OCPI/OCPP의 계층·역할을 설계에 반영할 수 있다. |
| 운영·생산 계약 | `partial` | quota·오류·freshness 정책은 작성했지만 실제 운영계정 한도, Keco 상태 enum, KSGA/NIER 세부 가이드는 추가 확인이 필요하다. |

## 후속 조사

1. **우선순위: P0**
   - **질문 또는 불확실성:** 최신 Keco v1.25 가이드의 `stat` 숫자별 의미와 `getChargerInfo` 전체 스키마는 무엇인가?
   - **기대 의사결정 영향:** UI 상태 표시, 상태 enum, station/chager join key를 확정한다.
   - **권장 검증:** 포털 가이드 다운로드와 승인 키를 이용한 무작위 지역 소량 호출, 키 제거 XML fixture 생성.

2. **우선순위: P0**
   - **질문 또는 불확실성:** 운영계정 quota 증량 조건·실제 응답 지연·지역별 갱신 편차는 어떠한가?
   - **기대 의사결정 영향:** polling 주기, 저장소 크기, SLO와 비용을 확정한다.
   - **권장 검증:** 운영계정 신청 전 공식 문의 및 제한된 기간의 수집 telemetry 측정.

3. **우선순위: P1**
   - **질문 또는 불확실성:** KSGA 승인 후 실제 JSON endpoint·사업자 범위·갱신 SLA는 무엇인가?
   - **기대 의사결정 영향:** 두 소스 병합 여부와 source priority를 결정한다.
   - **권장 검증:** KSGA 승인·이용가이드 확인 후 동일 지역·동일 시간대 fixture 비교.

4. **우선순위: P1**
   - **질문 또는 불확실성:** 차량 인증 API의 승인 후 endpoint·검색 파라미터·변경 이력은 무엇인가?
   - **기대 의사결정 영향:** 차량 카탈로그 provider의 pagination·동기화 전략을 확정한다.
   - **권장 검증:** 최신 Swagger/가이드와 인증 완료·반납·과거 데이터 경계 fixture를 확보한다.
