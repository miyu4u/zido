# EV Charging API 구현 재리뷰

- 리뷰 범위: `charger-domain`, `charger-providers`, `charger-storage`, HTTP charging controller, MCP charging tools, 공통 telemetry
- 리뷰 방식: 변경 계약 추적, freshness/error/storage/security 고위험 경로 재검토, 집중 회귀 테스트 및 전체 검증 명령 실행

## 1. 최종 판정

핵심 충전 상태·freshness·오류·저장소 경계에서 이전 리뷰의 P0/P1 수준 결함은 확인되지 않았다. 기능 경계 기준으로는 Release Candidate 수준이다.

다만 계획 문서의 T-09 관측성 DoD는 아직 부분 충족이다. 실제 운영 release를 계획의 모든 acceptance 기준으로 판단하면 **Conditional / Partial**이며, retry 관측과 freshness/stale-ratio 관측을 보완한 뒤 최종 release 승인을 권고한다.

## 2. 이전 리뷰 주요 결함의 수정 확인

### 2.1 충전소 detail/MCP freshness 불일치 — 해결

station snapshot의 `sourceObservedAt`가 TTL을 초과했지만 개별 charger의 `statusUpdatedAt`만 최신인 경우, detail 또는 MCP 응답에서 `AVAILABLE`이 노출될 수 있었던 문제를 수정했다.

현재 `ChargerService`는 station snapshot freshness를 함께 확인하고, snapshot이 만료되었으면 charger 상태를 강제로 stale 재계산한다. 이에 따라 HTTP detail, MCP `charger_status`, 검색 결과가 TTL 이후 `AVAILABLE`을 노출하지 않는 동일한 의미를 사용한다.

관련 검증:

- station snapshot TTL 만료 + 최신 charger timestamp 회귀 테스트
- HTTP detail stale 응답 테스트
- MCP charger status 실행 테스트

### 2.2 KECO XML envelope 검증 부족 — 해결

`resultCode`와 body가 존재하더라도 인식 가능한 `<header>` 또는 `<cmmMsgHeader>`가 없으면 응답을 거부하도록 수정했다. 정상 응답, `NO_DATA (03)`, pagination, item identity 및 malformed response 경계를 함께 검증한다.

### 2.3 SQLite monotonic update와 query cache freshness — 해결

다음 저장소 경계를 보완했다.

- 오래된 `observedAt`/`statusUpdatedAt` 데이터가 최신 charger 상태를 덮어쓰지 않음
- source가 지정된 station 조회에서 다른 source의 station을 fallback하지 않음
- 모든 charger row가 monotonic guard에 의해 거부된 refresh는 query TTL과 membership를 갱신하지 않음
- 잘못된 `options.now` 입력은 stale로 처리하여 TTL 검사를 우회하지 않음

### 2.4 보안·오류 계약 — 해결 확인

- 원격 KECO endpoint는 HTTPS를 요구함
- insecure HTTP는 injected fetch를 사용하는 localhost 테스트 adapter에 한정됨
- 외부 URL의 전체 query string을 redaction함
- provider raw error와 ServiceKey가 HTTP/MCP public error에 노출되지 않음
- rate limit은 안정적인 `RATE_LIMITED` 계약과 HTTP 429로 변환됨

## 3. 잔여 발견사항

### Medium — retryCount가 실제 retry 횟수를 반영하지 않음

`RefreshCoordinator`는 retryable provider 오류에 대해 재시도하지만, `KecoProvider`가 기록하는 telemetry event는 성공·실패 모두 `retryCount: 0`이다. coordinator의 실제 시도 횟수가 provider telemetry에 전달되지 않으므로 timeout 및 일시적 upstream 오류의 retry pressure를 정확히 분석할 수 없다. `QUOTA_EXHAUSTED`는 retry 대상이 아니므로 quota 자체의 관측 공백은 다음 finding에서 별도로 다룬다.

영향:

- retry가 발생해도 telemetry상 단일 시도처럼 보임
- timeout과 일시적 upstream failure의 운영 분석 정확도가 낮아짐

권고:

- coordinator의 retry attempt를 provider telemetry에 전달하거나
- coordinator가 retry 시도/최종 실패 event를 별도로 기록하고 실제 retry count를 채울 것

### Medium — freshness/stale-ratio/alert signal의 runtime 연결 부족

`ChargerMetricEvent`에는 `freshness` 필드가 정의되어 있지만 실제 provider event에는 값이 채워지지 않는다. 또한 domain/coordinator 경로에서 stale ratio 및 timeout, schema failure, permission, quota 조건을 집계하는 runtime event가 확인되지 않았다.

bounded telemetry sink와 redaction된 provider endpoint/result/status/latency/item count/quota event는 구현되어 있으나, T-09가 요구하는 freshness 품질 및 alertability 전체를 충족하지는 않는다.

권고:

- coordinator/domain 계층에서 derived freshness 및 stale ratio를 기록할 것
- timeout/schema failure/permission/quota별 counter 또는 alert classifier를 추가할 것
- provider retry attempt와 결합해 운영 대시보드에서 refresh 품질을 구분할 것

## 5. 미검증 경계

다음 경계는 fixture 및 unit/contract test만으로 확인되었으며, 재리뷰에서도 실제 운영 환경 검증은 수행하지 않았다.

- live KECO key/quota를 사용한 smoke test
- multi-replica 또는 shared-filesystem SQLite 동작
- upstream KECO schema 및 contract drift

## 6. 결론 및 우선순위

1. 핵심 사용자 응답의 freshness, effective status, stale fallback, rate-limit/error contract는 이전 리뷰 대비 개선되었으며 P0/P1 blocker가 없다.
2. HTTPS, 외부 query redaction, XML envelope validation, monotonic storage 경계는 release 전제에 부합한다.
3. 계획 전체의 `execution_status: completed`를 최종 승인하려면 T-09의 실제 retry count, freshness, stale ratio 및 alert signal을 runtime telemetry에 연결해야 한다.
4. 운영 관측성이 별도 release gate가 아니라면 현재 구현은 기능 기준 Release Candidate로 분류할 수 있다.
