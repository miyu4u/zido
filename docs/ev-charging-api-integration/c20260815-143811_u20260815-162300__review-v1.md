## 3. 주요 발견사항

### P0 — station detail/MCP 상태가 TTL 이후에도 `AVAILABLE`일 수 있음

**파일**

- `libs/charger-domain/src/charger-service.ts:123-142`
- `libs/charger-domain/src/charger-service.ts:225-233`
- `apps/http-server/src/charging/charging.controller.ts:65-83`

`getSnapshot()` 경로는 `recalculateFreshness()`를 호출하지만, `getStation()`은 storage 결과를 그대로 반환한다. 따라서 다음 경로에서는 저장 당시 `FRESH`였던 상태가 시간이 지나도 그대로 노출된다.

```text
HTTP /v1/charging-stations/{stationId}
MCP charger_status
  -> ChargerService.getStatus()
  -> getStation()
  -> store.findStation()
  -> freshness 재계산 없음
```

오래된 charger가 `AVAILABLE`로 계속 응답될 수 있다. 이는 계획의 핵심 불변식인 `R-04`, T-03의 “TTL 초과 AVAILABLE 금지”를 위반한다.

**권고**

- `getStation()` 반환 전에 모든 charger의 freshness와 effective status를 현재 시각 기준으로 재계산
- detail 응답도 snapshot/query TTL과 동일한 정책 사용
- 이 경로에 stale `AVAILABLE -> UNKNOWN` 테스트 추가

### High — provider quota/rate-limit 오류가 실제로 `RATE_LIMITED`로 매핑되지 않음

**파일**

- `libs/charger-domain/src/charger-service.ts:102-117`
- `apps/http-server/src/charging/charging.controller.ts:129-165`

HTTP controller에는 `RATE_LIMITED -> 429` 매핑이 있지만, 실제 domain 흐름에서는 provider 오류 종류를 구분하지 않는다.

```ts
catch (err) {
  refreshErr = err
  // ...
}

throw new McpException(
  // ...
  'SNAPSHOT_UNAVAILABLE',
  503,
)
```

실제 KECO `RATE_LIMITED`, `QUOTA_EXHAUSTED`, authentication 오류는 모두 cold cache에서 `SNAPSHOT_UNAVAILABLE / 503`으로 변환된다. 계획 T-07의 `RATE_LIMITED` 계약은 fake service가 직접 `McpException`을 던지는 테스트에서만 검증된다.

**권고**

- `KecoProviderError.failureKind`를 domain public error로 안전하게 매핑
- rate limit은 `RATE_LIMITED / 429`
- quota/authentication은 정책에 맞는 stable code로 변환
- raw provider message와 key는 계속 외부 응답에서 제외

### High — stale fallback 재조회에서 TTL을 전달하지 않음

**파일**

- `libs/charger-domain/src/charger-service.ts:102-110`

refresh 실패 후 다음과 같이 TTL 없이 snapshot을 다시 읽는다.

```ts
const snapshot = await this.store.readQuerySnapshot(queryKey)
```

이 때문에 `QuerySnapshotBundle.isStale`가 다시 계산되지 않고 `false`로 남을 수 있다. 이후 `searchNearby()`는 `snapshot.isStale`를 기준으로 강제 stale 처리하므로 stale fallback의 freshness 표현이 일관되지 않다.

계획 T-06은 “refresh 실패 시 stale snapshot은 STALE로 반환”을 요구한다.

**권고**

- 재조회에도 `{ ttlMs }`와 기준 시각을 전달
- refresh 실패로 fallback한 경우 명시적으로 stale 상태를 유지
- `observedAt`은 절대 갱신하지 않음
- refresh 실패 + stale fallback의 실제 HTTP/MCP 테스트 추가

### High — KECO `NO_DATA (03)`가 정상적인 빈 snapshot으로 처리되지 않음

**파일**

- `libs/charger-providers/src/keco/keco-contracts.ts:88-170`
- `libs/charger-providers/src/keco/keco-xml-parser.ts:120-125`

`KECO_RESULT_CODES.NO_DATA`는 선언되어 있지만 `classifyKecoResultCode()`에 별도 case가 없다. 따라서 `03`은 default로 들어가 `UPSTREAM_UNAVAILABLE`이 된다. XML parser도 `resultCode !== '00'`이면 무조건 예외를 던진다.

결과적으로 데이터가 없는 지역의 정상 응답이 빈 결과 snapshot으로 저장되지 않고 `SNAPSHOT_UNAVAILABLE`로 끝날 수 있다.

계획 T-04는 empty snapshot과 cache miss를 구분하도록 요구하고, 계획의 목표도 위치 검색에서 빈 결과를 정상적으로 반환하는 것이다.

**권고**

- `03`을 정상적인 empty page로 정의하거나 공식 계약에 맞는 별도 semantics를 결정
- 빈 result를 `itemCount: 0` snapshot으로 저장
- `03` fixture와 empty-region end-to-end 테스트 추가

### High — charger upsert가 오래된 원천 데이터를 최신 데이터 위에 덮어쓸 수 있음

**파일**

- `libs/charger-storage/src/sqlite-charger-snapshot-store.ts:147-165`

charger UPSERT는 기존 `observed_at` 또는 `status_updated_at`과 비교하지 않고 무조건 새 값을 덮어쓴다.

동시 수집 또는 지연된 provider 응답에서 오래된 응답이 늦게 도착하면 다음과 같은 회귀가 가능하다.

```text
최신 상태 저장
  -> 오래된 상태가 뒤늦게 저장
  -> 최신 상태가 과거 상태로 회귀
```

계획의 data guardrail인 “오래된 원천 상태를 fresh로 연장하지 않는다”를 충분히 보장하지 못한다.

**권고**

- `status_updated_at` 또는 source version을 기준으로 monotonic upsert
- timestamp parsing 실패 시 보수적으로 기존 상태 유지 또는 `UNKNOWN`
- out-of-order write 테스트 추가

### Medium — source 지정 조회가 다른 source의 station을 반환할 수 있음

**파일**

- `libs/charger-storage/src/sqlite-charger-snapshot-store.ts:477-486`

`findStation()`은 source/operator를 사용한 composite key 조회가 실패해도 bare `station_id`로 다시 조회한다.

따라서 `keco:ME:ST-001`이 없는데 다른 source에 `ST-001`이 있으면 요청한 source가 아닌 station을 반환할 수 있다.

현재 MVP는 KECO 단일 source이므로 즉시 재현 가능성은 낮지만, canonical source identity 계약과 충돌한다.

**권고**

- source/operator가 전달된 경우 composite key 조회 실패 시 즉시 `null`
- bare station ID 조회는 source 미지정 호출에서만 허용

### Medium — `regionCode`와 `periodMinutes` 설정이 실제 provider 요청에 사용되지 않음

**파일**

- `libs/common/src/config.ts`
- `libs/charger-domain/src/charger-service.ts:166-175`
- `libs/charger-domain/src/refresh-coordinator.ts:75-97`

설정에는 다음 값이 존재한다.

- `CHARGER_REGION_CODE`
- `CHARGER_STATUS_PERIOD_MINUTES`

하지만 `searchNearby()`는 `zcode`를 전달하지 않고, `RefreshCoordinator`도 status page 요청에 `period`를 전달하지 않는다. 또한 cache key에도 region/filter 범위가 포함되지 않는다.

결과적으로 설정값을 변경해도 실제 수집 범위가 달라지지 않는다.

**권고**

- provider 요청에 region/period를 실제 전달
- 해당 값들을 query key에 포함
- 설정값 변경에 따른 cache collision 테스트 추가

### Medium — XML schema failure를 충분히 감지하지 못함

**파일**

- `libs/charger-providers/src/keco/keco-xml-parser.ts:120-171`

parser는 주로 `resultCode`만 확인하고, body/pagination/item 구조가 누락된 XML을 빈 성공 page처럼 처리할 수 있다. 계획 T-05는 XML parse/schema failure를 typed failure로 분류하도록 요구한다.

**권고**

- 필수 header/body/pagination 구조 검증
- 필수 item field 누락 여부 검증
- malformed XML, body 누락, invalid pagination fixture 추가

### Medium — HTTPS와 외부 query redaction guardrail이 불완전함

**파일**

- `libs/charger-providers/src/keco/keco-provider.ts:42-47`
- `libs/charger-providers/src/keco/keco-redact.ts:6-14`
- 계획 `docs/ev-charging-api-integration/c20260815-000831_u20260815-162300__plan-v1.md:235`

`endpoint` 환경변수에 `http://`를 넣어도 차단하지 않는다. 그러면 ServiceKey가 평문 HTTP로 전송될 수 있다.

또한 redaction은 ServiceKey와 Authorization/Bearer 일부만 가리고, `pageNo`, `zcode`, 기타 외부 query 전체는 남긴다. 계획의 guardrail은 외부 query 전체를 logger/trace/error/fixture 경계 밖으로 제거하도록 되어 있다.

**권고**

- production endpoint는 `https:`만 허용
- fixture/test에서만 명시적인 local HTTP adapter 허용
- 로그용 URL은 query 전체 제거 또는 허용된 비밀 없는 field만 재구성

### Medium — T-09 관찰성 구현이 runtime에 연결되지 않음

**파일**

- `libs/common/src/charger-observability.ts`
- `libs/charger-providers/src/charger-providers.module.ts`
- `libs/charger-providers/src/keco/keco-provider.ts`

`ChargerTelemetry`는 정의되어 있지만 `ChargerProvidersModule`에서 provider에 주입되지 않는다. 따라서 runtime에서는 다음 항목이 실제로 기록되지 않는다.

- retry count
- freshness
- quota/rate-limit signal
- HTTP error status
- stale ratio
- endpoint-level charging metrics

또한 telemetry event 배열은 process lifetime 동안 계속 증가해 bounded sink가 아니다.
