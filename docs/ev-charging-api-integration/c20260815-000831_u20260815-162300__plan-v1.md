# 목표 및 문제, 사용자의 질문

구현 대상은 [전기차 충전 상태 확인 설계](./c20260814-235527_u20260815-162300__design-v1.md)다. KECO의 충전소·충전기 상태를 외부 API에서 받아 로컬 SQLite snapshot에 저장하고, 캐시가 유효한 동안에는 외부 API를 호출하지 않으며, 캐시 miss 또는 만료 때만 cache-aside 수집을 수행한다. 저장된 domain 결과는 HTTP API와 MCP tool에서 동일하게 사용한다.

사용자는 “수집 → 로컬 캐싱 → 캐싱 기간 내 반환” 구조를 선택했다. 따라서 MVP에는 상시 수집 scheduler 또는 별도 collector worker를 포함하지 않는다. 대신 지역 또는 조회 key별 single-flight를 사용해 cache miss 동시 호출을 막는다.

## 목표에 대한 이해

- 위치와 반경으로 충전소를 조회하고 각 charger의 상태·원천 상태값·원천 갱신 시각·관측 시각·freshness를 반환한다.
- `AVAILABLE`은 상태 매핑이 확인되고 TTL 이내인 경우에만 사용자 상태로 노출한다. stale 또는 미확인 상태는 `UNKNOWN`으로 보존한다.
- HTTP REST controller와 MCP tool은 `charger-domain` service만 호출한다. 두 transport가 서로 다른 상태 규칙이나 provider 호출을 갖지 않는다.
- KECO API key, raw response, 외부 오류 세부사항은 로그·trace·사용자 응답에 노출하지 않는다.
- 현재 저장소의 `map-providers` 계약과 기존 장소 API·MCP tool·HTTP session transport는 변경하지 않는다.

  - MVP에는 상시 수집 scheduler 또는 별도 worker를 두지 않는다.
- 미해결 질문:

### C2 — 배경 정보와 모드 선택

- 관측 사실:
  - 설계 문서는 KECO `getChargerStatus`를 HTTPS REST/XML, `ServiceKey`, 페이지네이션, `period`, `zcode` 계약으로 기록한다.
  - `stat`, `statUpdDt`, `busiId`, `statId`, `chgerId`가 상태 응답의 핵심 필드다.
  - 현재 저장소는 `libs/place-domain`, `libs/map-providers`, `libs/mcp-runtime`과 HTTP/stdio/CLI application으로 구성되어 있다.
  - HTTP와 stdio는 `McpRuntimeModule`을 사용하고, CLI는 `PlaceDomainModule`을 직접 사용한다.
  - `package.json`에 SQLite 또는 ORM 의존성은 관측되지 않았다.
  - 현재 저장소에 충전 domain, storage, collector application은 존재하지 않는다.
- 해석:
  - 충전 상태는 기존 지도 `Provider`에 추가하지 않고 별도 domain/provider/storage 경계를 만들어야 한다.
  - cache-aside MVP에서는 사용자 요청이 cache hit일 때 외부 API를 호출하지 않으며, miss 시 domain 내부 refresh coordinator가 provider를 호출한다.
  - SQLite는 단일 노드·단일 writer MVP에 적합하지만 다중 replica 공유 저장소로 간주할 수 없다.
- 미검증 경계:
  - KECO 최신 `stat` 숫자별 의미와 `getChargerInfo` 전체 schema·join key는 공식 guide와 sanitized fixture 확인이 필요하다.
  - 현재 저장소에는 SQLite driver와 XML parser가 없으므로 구현 시 runtime-compatible dependency를 추가해야 한다.
  - 승인 key를 사용하는 live endpoint smoke test와 실제 운영 quota는 아직 실행·확인하지 않았다.
- 선택 모드: deep
- 선택 이유: 새 domain·provider·storage·public HTTP contract·MCP registration·외부 계약 fixture가 함께 바뀌며, SQLite concurrency와 미확인 공공 API schema라는 복구 비용 높은 경계가 있다. 구현은 실행하지 않고 계획만 작성한다.

# User-Facing

## 작업 요약 및 브리핑 설명

이번 계획은 KECO 충전 상태를 사용자 요청마다 직접 조회하는 대신, SQLite snapshot을 cache-aside로 관리하는 읽기 전용 MVP를 구현한다. 유효한 캐시가 있으면 빠르게 반환하고, 캐시가 없거나 만료되면 한 요청만 외부 API를 호출해 결과를 저장한 뒤 응답한다. 외부 호출 실패 시 stale snapshot이 있으면 신선도 정보를 포함해 반환하고, snapshot이 전혀 없으면 명시적 unavailable 오류를 반환한다.

사용자에게 추가되는 표면은 다음과 같다.

- HTTP `GET /v1/charging-stations`
- HTTP `GET /v1/charging-stations/{stationId}`
- MCP `charger_search_nearby`
- MCP `charger_status`

MVP의 사용자-facing 의미는 외부 API의 숫자 상태보다 안전한 domain enum과 `freshness`를 기준으로 한다.

## 관측 시점의 현재 구성

```text
HTTP app ────────────────┐
                         ├─> McpRuntimeModule ─> PlaceDomainModule ─> MapProvidersModule
stdio app ──────────────┘

CLI app ───────────────────> PlaceDomainModule ─> MapProvidersModule
```

현재 `PlaceService`는 장소 resolve/search/geocode를 소유하고 `ProviderRouterService`에 의존한다. MCP tool registration은 `libs/mcp-runtime/src/register-tools.ts`에서 장소 domain을 호출한다. HTTP app은 Streamable HTTP MCP transport와 session registry를 소유하며, 일반 충전 REST API controller는 아직 없다.

현재 문제는 충전 상태가 장소 검색과 다른 계약을 요구한다는 점이다. 상태는 원천 pagination, `statUpdDt`, TTL, source conflict, stale fallback, API key redaction을 필요로 하므로 기존 지도 `Provider`에 메서드를 추가하면 책임이 섞인다.

## 개선 후 예상 구성

```text
HTTP REST / MCP request
          │
          ▼
   charger-domain service
      │           │
      │           └─ cache miss/expired
      │                    │
      ▼                    ▼
SQLite snapshot ◄── single-flight refresh ── KECO XML provider
      │
      └── cache hit 또는 stale fallback 응답
```

예상 책임은 다음과 같다.

- `charger-domain`: canonical station/status, freshness, effective status, 반경 검색, cache-aside orchestration
- `charger-providers`: KECO XML query·parser·resultCode·외부 오류 분류
- `charger-storage`: SQLite schema, snapshot read/write, TTL metadata, lock/idempotent upsert
- `http-server`: query validation, REST response/error/header 변환
- `mcp-runtime`: 동일 domain service를 호출하는 두 charger tool 등록
- `common/config`: SQLite path, TTL, timeout, retry, source 설정

상시 scheduler·별도 worker는 MVP에서 제외한다. 향후 사전 수집 또는 다중 replica가 필요해지면 cache-aside 계획을 새 revision으로 확장한다.

## 변경 영향

- `P0-1`: 새로운 충전 REST endpoint와 MCP tool이 추가된다. 기존 장소 endpoint와 기존 MCP tool은 유지한다.
- `P0-2`: cache miss/만료 요청은 외부 API latency와 외부 실패를 경험할 수 있다. `FRESH`, `STALE`, `UNKNOWN`과 명시적 unavailable 오류로 계약한다.
- `P1-1`: SQLite 파일은 단일 노드·단일 writer 범위다. 다중 replica 또는 shared filesystem 운영은 지원하지 않는다.
- `P1-2`: cache-aside에서는 사용자 요청이 cache miss 때 외부 API를 호출할 수 있다. 이는 기존 설계의 snapshot-only 원칙에 대한 명시적 MVP 예외다.
- `P1-3`: 외부 API key와 승인된 fixture가 필요한 live contract 검증은 기본 CI와 분리한다.
- `P2-1`: 충전 domain과 storage가 추가되므로 `nest-cli.json`, path alias, 구조 문서 갱신이 필요하다.

## 사용자가 결정한 부분

### HD-1 — Snapshot persistence backend

- 필요한 이유: 저장 schema, concurrency, deployment topology, cache read/write contract를 결정한다.
- 현재 선택: `HD-1-A2`
- 선택지:
  - `HD-1-A1`: PostgreSQL. 다중 replica와 durable 운영에 적합하지만 DB infrastructure, migration, connection 설정이 추가된다.
  - `HD-1-A2`: SQLite. 단일 노드·로컬 cache MVP를 단순하게 구현하며 별도 DB 운영이 없다.
  - `HD-1-A3`: backend-neutral. storage port만 만들고 실제 cache 저장을 후속 결정으로 남기므로 이번 end-to-end 범위가 축소된다.
- 기본 권고안: `HD-1-A2`
- 권고 이유: 사용자가 로컬 캐시 구조를 선택했고 현재 repository에 DB infrastructure가 없으며, MVP의 bounded scope와 일치한다.

### HD-2 — External collection strategy

- 필요한 이유: 외부 API 호출 위치, cold miss latency, 운영 process, stale fallback을 결정한다.
- 현재 선택: `HD-2-A1`
- 선택지:
  - `HD-2-A1`: cache-aside. TTL 내 cache hit는 외부 호출 없이 반환하고, miss/만료 때 single-flight로 한 번 수집한다.
  - `HD-2-A2`: snapshot-only + scheduler. 사용자 요청은 snapshot만 읽고 별도 scheduler가 사전 수집한다.
- 기본 권고안: `HD-2-A1`
- 권고 이유: scheduler·worker를 추가하지 않고 로컬 캐시 기반 MVP를 빠르게 검증할 수 있다. cold miss latency와 stampede 방지는 명시적 계약으로 관리한다.

## 제한된 preference 결정

### SD-1 — MVP source 범위

- 필요한 이유: provider 수와 source conflict를 제한해 첫 구현의 복구 범위를 통제한다.
- 현재 선택: `SD-1-A1`
- 선택지:
  - `SD-1-A1`: KECO만 구현하고 KSGA·차량 인증·OCPI·OCPP는 후속 범위로 둔다.
  - `SD-1-A2`: KECO와 KSGA를 동시에 구현해 source 교차검증까지 포함한다.
- 기본 권고안: `SD-1-A1`
- 권고 이유: KSGA의 실제 schema·coverage·SLA가 아직 검증되지 않았고, KECO가 MVP의 공식 1순위 source다.

## 가정들

- `AS-1`: MVP는 단일 노드, 단일 HTTP process, 단일 SQLite writer로 운영한다.
  - 이유: SQLite 파일은 다중 replica의 공용 durable store가 아니며 cache-aside의 writer lock 범위를 제한해야 한다.
  - 대안: PostgreSQL 또는 외부 durable store로 전환하고 collector/read replica topology를 별도 설계한다.
  - 트레이드오프: 운영 단순성은 높지만 수평 확장과 장애 격리가 제한된다.
  - 깨질 때의 처리: multi-replica, shared filesystem, HA 또는 별도 worker 요구가 나오면 `replan-required`로 새 revision을 만든다.
- `AS-2`: KECO 최신 활용가이드와 key 제거 fixture는 status mapping·info join 구현 전에 확보된다.
  - 이유: 공개 조사만으로 `stat` 의미와 `getChargerInfo` 전체 schema를 안전하게 추정할 수 없다.
  - 대안: 원천값만 보존하는 status-only contract로 축소한다.
  - 트레이드오프: 위치 기반 station 검색과 `AVAILABLE` 매핑을 완성하지 못한다.
  - 깨질 때의 처리: fixture가 없으면 `T-01`을 blocked로 기록하고 downstream 구현을 시작하지 않는다. scope 축소는 사용자 승인 없이는 하지 않는다.
- `AS-3`: 기본 CI는 fixture·domain·storage·HTTP/MCP contract test만 실행하며 live external call은 opt-in이다.
  - 이유: API key와 외부 quota·network 상태를 CI 성공 조건으로 만들지 않는다.
  - 대안: 별도 protected environment에서 승인 key smoke test를 실행한다.
  - 트레이드오프: 기본 CI는 실제 provider availability를 증명하지 않는다.
  - 깨질 때의 처리: live test가 필요해지면 secret·egress·quota owner를 정한 뒤 검증 task를 별도로 승인한다.
- `AS-4`: SQLite driver와 XML parser는 현재 runtime과 package policy에 맞는 최소 dependency로 선택한다.
  - 이유: 현재 package에 해당 dependency가 없고 구체적인 library 선택은 구현 환경 검증이 필요하다.
  - 대안: runtime 내장 capability 또는 별도 adapter를 사용한다.
  - 트레이드오프: native dependency는 배포 호환성 비용을, pure JS/WASM 계열은 성능·파일 locking 검토 비용을 만든다.
  - 깨질 때의 처리: driver가 single-writer transaction, prepared query, file persistence를 만족하지 못하면 dependency 선택을 재검토하되 storage backend 결정 자체는 바꾸지 않는다.

## 결정 트리

- `DT-1`: 조회 시 cache hit인지 먼저 판정한다.
  - 결정 이유: 캐시 기간 내에는 외부 API를 호출하지 않는 사용자 결정 때문이다.
  - 근거: `HD-2-A1`, `AS-1`
  - 예상 대안:
    - `DT-1-A-1`: 유효 cache 반환
    - `DT-1-A-2`: miss/만료이면 refresh coordinator로 이동
- `DT-2`: 동일 cache key에 이미 refresh가 있으면 새 provider call을 만들지 않는다.
  - 결정 이유: cache stampede와 quota 초과를 막기 위해서다.
  - 근거: `HD-2-A1`, `R-05`
  - 예상 대안:
    - `DT-2-A-1`: 진행 중 refresh를 제한 시간 동안 기다린다.
    - `DT-2-A-2`: 대기 timeout 후 stale cache 또는 unavailable을 반환한다.
- `DT-3`: refresh가 실패하면 stale snapshot의 존재 여부를 판정한다.
  - 결정 이유: 일시적 외부 장애가 이미 관측한 데이터를 즉시 삭제하지 않도록 한다.
  - 근거: `R-04`, `AS-3`
  - 예상 대안:
    - `DT-3-A-1`: stale snapshot과 source error summary를 반환한다.
    - `DT-3-A-2`: snapshot이 없으면 `SNAPSHOT_UNAVAILABLE`을 반환한다.
- `DT-4`: raw status mapping 또는 원천 시각이 불명확하면 안전한 상태를 선택한다.
  - 결정 이유: 확인되지 않은 숫자를 `AVAILABLE`로 추정하지 않기 위해서다.
  - 근거: `R-01`, `R-04`, `AS-2`
  - 예상 대안:
    - `DT-4-A-1`: mapped status를 보존하고 effective status를 `UNKNOWN`으로 둔다.
    - `DT-4-A-2`: 매핑 fixture가 확인된 상태만 사용자 enum으로 노출한다.

# Agent-Facing

## Drift Guardrail

- 반드시 포함: KECO read-only status/info adapter, SQLite snapshot cache, cache-aside single-flight, freshness-aware domain, HTTP REST contract, MCP charger tools, fixture-based verification.
- 변경 금지: `libs/map-providers`의 `Provider` interface, 기존 `PlaceService` public contract, 기존 `place_*` MCP tool 이름·입력·출력, HTTP Streamable MCP session registry, stdio stdout JSON-RPC 계약.
- 하지 않을 일: KSGA provider, 차량 인증 provider, OCPI, OCPP, 원격 시작·중지·결제·예약, 실시간 운영 scheduler, 별도 collector worker, live key를 기본 CI에 넣는 일, 확인되지 않은 KECO status 숫자·info schema 추정.
- 보안 guardrail: Service Key와 Authorization 및 외부 query 전체를 logger·trace·error·fixture에서 redact한다. raw response는 제한된 sanitized fixture 경계 밖으로 내보내지 않는다.
- 데이터 guardrail: `(source, operatorId, stationId, chargerId)`를 upsert key로 사용하고 `observedAt`로 오래된 원천 상태를 fresh로 연장하지 않는다.
- 재계획 신호: 다중 replica/HA, shared SQLite filesystem, scheduler/worker 도입, PostgreSQL 전환, KSGA 병합 요구, 원격 명령·세션·결제 요구, KECO 계약 변경으로 기존 API contract를 보존할 수 없는 경우.
